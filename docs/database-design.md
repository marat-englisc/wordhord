# Проектирование моделей и индексов

Текущее хранение разделено на `content.db` и `users.db`; устройство описано в
[databases.md](databases.md). Индексы и внутренние FK сохраняются. Четыре ссылки
пользовательских таблиц на контент проверяются TEMP-триггерами соединения, поскольку
SQLite не поддерживает FK между файлами.

Схема разделяет словарь (`deck`, `card`, `card_meaning`, примеры и атрибуты), связи пользователя с колодами, состояние изучения каждого значения и журнал повторений. Уникальность пары `(user_id, card_meaning_id)` сохраняет одно состояние изучения на пользователя и значение.

Поиск пользователя по `telegram_id` обслуживает индекс `UNIQUE`. Индексы также поддерживают репозитории, каскадное удаление, очередь FSRS и историю повторений.

## Индексы

| Таблица | Индекс / ключ | Назначение |
| --- | --- | --- |
| `user` | `UNIQUE(telegram_id)` | Регистрация и поиск пользователя |
| `card` | `(deck_id)` | Карточки колоды; проверка `ON DELETE RESTRICT` |
| `card_meaning` | `(card_id)` | Значения карточки и каскадное удаление |
| `card_example` | `(card_meaning_id)` | Примеры значения и каскадное удаление |
| `card_meaning_attribute` | `UNIQUE(card_meaning_id, attribute_id, value)` | Несколько различных значений атрибута; поиск по значению карточки |
| `card_meaning_attribute` | **`(attribute_id)`** | Обратный поиск и удаление атрибута |
| `user_deck` | `UNIQUE(user_id, deck_id)` | Колоды пользователя; защита от дублирования связи |
| `user_deck` | **`(deck_id)`** | Пользователи колоды и удаление колоды |
| `user_card_meaning` | `UNIQUE(user_id, card_meaning_id)` | Уникальное состояние изучения; поиск по пользователю |
| `user_card_meaning` | `(user_id, due)` | `WHERE user_id = ? AND due <= ? ORDER BY due, id` |
| `user_card_meaning` | **`(card_meaning_id)`** | Состояния изучения значения и каскадное удаление |
| `user_card_meaning` | **`UNIQUE(id, user_id, card_meaning_id)`** | Родительский ключ составной ссылки журнала |
| `user_card_meaning_review` | `(user_id, review)` | История пользователя по времени |
| `user_card_meaning_review` | **`(user_card_meaning_id, review)`** | История конкретного состояния изучения и каскадное удаление |

Индексы обратных связей поддерживают поиск по родительскому ID и каскадное удаление. Для очереди и истории используется порядок по времени и `id`.

Отдельные индексы на `user_id` в таблицах связей и на `card_meaning_id` в таблице атрибутов уже покрыты левым префиксом существующих составных индексов. Дополнительные копии этих индексов увеличивали бы стоимость записи. Подход основан на [планировщике запросов SQLite](https://www.sqlite.org/queryplanner.html) и [рекомендациях по индексам внешних ключей](https://www.sqlite.org/foreignkeys.html#required_and_suggested_database_indexes).

## Согласованность журнала

`(user_card_meaning_id, user_id, card_meaning_id)` ссылается на одну соответствующую тройку в `user_card_meaning`. Поля пользователя и значения позволяют напрямую читать историю, а их согласованность гарантирует база. Каскад от пользователя или значения проходит через состояние изучения к журналу.

Составной `UNIQUE` в родительской таблице логически следует из уникального `id`, однако SQLite требует точного соответствия набора столбцов родительскому уникальному ключу для составного внешнего ключа. Это стоимость прямого доступа к истории по пользователю при проверке полной принадлежности записи.

## Данные FSRS и даты

`state` типизирован как `State` и ограничен значениями `0–3`. `rating` типизирован как `Rating` и допускает `0–4`, включая `Manual = 0`. Счётчики должны быть целыми и неотрицательными; стабильность — числовой и неотрицательной, сложность — числовой в диапазоне `0–10`. Ноль разрешён для начального состояния. Проверки работают на уровне SQLite, включая прямые SQL-запросы.

`lastElapsedDays` и `learningSteps` соответствуют [ReviewLog TS-FSRS](https://open-spaced-repetition.github.io/ts-fsrs/interfaces/ReviewLog.html). Оба поля обязательны, должны быть целыми и неотрицательными и сохраняются из результата планировщика.

`due`, `lastReview`, `review` и `lastReviewedAt` сохраняют `Date` и миллисекунды через `timestamp_ms`. `updatedAt` заполняется при вставке и обновлении через [Drizzle `$onUpdate`](https://orm.drizzle.team/docs/sqlite/column-types); явно переданное значение имеет приоритет. Прямой SQL обходит этот механизм ORM.

## Грамматика

`rule` содержит название и общий порядок правил. `rule_section` разбивает правило на разделы; примеры и блоки основной информации относятся к разделу, изображения — к правилу. Внешние ключи этой структуры корректны и используют `ON DELETE CASCADE`.

`order` у правил, разделов, изображений, примеров и блоков информации задаёт порядок при редактировании материала. Для дочерних элементов значение по умолчанию — `0`; сортировать следует по `order`, затем по `id`. Одинаковые позиции разрешены: вставка нового элемента и перестановка соседних элементов не требуют временного нарушения уникальности. Позиции проверяются как целые неотрицательные числа.

| Таблица | Индекс / ключ | Назначение |
| --- | --- | --- |
| `rule` | `(order)` | Общий список правил в порядке `order, id` |
| `rule_section` | `(rule_id, order)` | Разделы правила в заданном порядке и каскадное удаление |
| `rule_image` | `(rule_id, order)` | Изображения правила в заданном порядке и каскадное удаление |
| `rule_section_example` | `(rule_section_id, order)` | Примеры раздела в заданном порядке и каскадное удаление |
| `rule_section_primary_info` | `(rule_section_id, order)` | Блоки информации раздела в заданном порядке и каскадное удаление |
| `user_rule` | `UNIQUE(user_id, rule_id)`, `(rule_id)` | Уникальная связь пользователя с правилом и поиск в обоих направлениях |
| `user_rule_comment` | `UNIQUE(user_id, rule_id)`, `(rule_id)` | Одна личная заметка на правило для каждого пользователя |

Составные индексы порядка покрывают поиск по родительскому ID левым префиксом и поддерживают сортировку по `order, id`.

По назначению `user_rule_comment` является личной заметкой, поэтому уникальность `(user_id, rule_id)` сохранена. Обновлять заметку можно через `UPDATE` или `onConflictDoUpdate` с этой парой в качестве `target`. Удаление пользователя удаляет его связи и заметки, сохраняя общий грамматический материал. Заметка ссылается непосредственно на пользователя и правило и может существовать независимо от записи `user_rule`.

TypeScript-поле изображения приведено к принятому в проекте имени `imageUrl`; SQL-столбец сохраняет имя `image_url`. `updatedAt` у правила и заметки корректно заполняется Drizzle. У правила это дата изменения его собственной строки; если приложение использует её как дату изменения всего материала, редактор должен также обновлять правило при изменении дочерних элементов в той же транзакции.

`npm run db:migrate` создаёт материалы грамматики в `content.db`, пользовательские связи и заметки — в `users.db`.
