# Проектирование моделей и индексов

Схема разделяет словарь (`deck`, `card`, `card_meaning`, примеры и атрибуты), связи пользователя с колодами, состояние изучения каждого значения и журнал повторений. Уникальность пары `(user_id, card_meaning_id)` сохраняет одно состояние изучения на пользователя и значение.

В приложении пока реализован только поиск пользователя по `telegram_id`; его уже обслуживает индекс `UNIQUE`. Остальные индексы оценены по связям моделей, каскадному удалению и ожидаемым запросам очереди и истории повторений. Это проверка схемы и планов запросов, а не измерение производительности рабочего приложения.

## Индексы

| Таблица | Индекс / ключ | Назначение |
| --- | --- | --- |
| `user` | `UNIQUE(telegram_id)` | Регистрация и поиск пользователя |
| `card` | `(deck_id)` | Карточки колоды; проверка `ON DELETE RESTRICT` |
| `card_meaning` | `(card_id)` | Значения карточки и каскадное удаление |
| `card_example` | `(card_meaning_id)` | Примеры значения и каскадное удаление |
| `card_meaning_attribute` | `UNIQUE(card_meaning_id, attribute_id, value)` | Несколько различных значений атрибута; поиск по значению карточки |
| `card_meaning_attribute` | **`(attribute_id)`** | Обратный поиск и удаление атрибута |
| `user_deck` | `UNIQUE(user_id, deck_id)` | Колоды пользователя; защита от дублирования связи |
| `user_deck` | **`(deck_id)`** | Пользователи колоды и удаление колоды |
| `user_card_meaning` | `UNIQUE(user_id, card_meaning_id)` | Уникальное состояние изучения; поиск по пользователю |
| `user_card_meaning` | `(user_id, due)` | `WHERE user_id = ? AND due <= ? ORDER BY due, id` |
| `user_card_meaning` | **`(card_meaning_id)`** | Состояния изучения значения и каскадное удаление |
| `user_card_meaning` | **`UNIQUE(id, user_id, card_meaning_id)`** | Родительский ключ составной ссылки журнала |
| `user_card_meaning_review` | `(user_id, review)` | История пользователя по времени |
| `user_card_meaning_review` | **`(user_card_meaning_id, review)`** | История конкретного состояния изучения и каскадное удаление |

Жирным отмечены добавленные индексы и ключ. До исправления четыре обратных поиска выполняли `SCAN`, включая сканирование уже существующих составных индексов. Теперь они выполняют `SEARCH` по подходящему индексу. Для очереди и истории проверен также порядок по времени и `id`, без временного B-tree для сортировки.

Отдельные индексы на `user_id` в таблицах связей и на `card_meaning_id` в таблице атрибутов уже покрыты левым префиксом существующих составных индексов. Дополнительные копии этих индексов увеличивали бы стоимость записи. Подход основан на [планировщике запросов SQLite](https://www.sqlite.org/queryplanner.html) и [рекомендациях по индексам внешних ключей](https://www.sqlite.org/foreignkeys.html#required_and_suggested_database_indexes).

## Согласованность журнала

Раньше три независимых внешних ключа проверяли лишь существование пользователя, значения и состояния изучения. Поэтому журнал мог ссылаться на существующее состояние другого пользователя или другого значения.

Теперь `(user_card_meaning_id, user_id, card_meaning_id)` ссылается на одну соответствующую тройку в `user_card_meaning`. Поля пользователя и значения остаются в журнале для совместимости и прямого чтения истории, но их согласованность гарантирует база. Каскад от пользователя или значения проходит через состояние изучения к журналу.

Дополнительный составной `UNIQUE` в родительской таблице логически следует из уникального `id`, однако SQLite требует точного соответствия набора столбцов родительскому уникальному ключу для составного внешнего ключа. Это осознанная стоимость сохранения текущих полей и доступа к истории по пользователю. Самостоятельные ссылки журнала на пользователя и значение заменены этой составной ссылкой.

## Данные FSRS и даты

`state` типизирован как `State` и ограничен значениями `0–3`. `rating` типизирован как `Rating` и допускает `0–4`, включая `Manual = 0`. Счётчики должны быть целыми и неотрицательными; стабильность — числовой и неотрицательной, сложность — числовой в диапазоне `0–10`. Ноль разрешён для начального состояния. Проверки работают на уровне SQLite, включая прямые SQL-запросы.

В журнал добавлены `lastElapsedDays` и `learningSteps` из [ReviewLog установленной версии ts-fsrs](https://open-spaced-repetition.github.io/ts-fsrs/interfaces/ReviewLog.html). Для старых записей оба поля остаются `NULL`: восстановить отсутствовавшие исторические значения достоверно нельзя. Новые записи должны получать эти поля из результата планировщика; обработка неполных старых логов требует явного решения вызывающего кода. Тест сохраняет полный результат FSRS, читает его обратно и проверяет `rollback`.

`due`, `lastReview`, `review` и `lastReviewedAt` сохраняют `Date` и миллисекунды через `timestamp_ms`. `updatedAt` заполняется при вставке и обновлении через [Drizzle `$onUpdate`](https://orm.drizzle.team/docs/sqlite/column-types); явно переданное значение имеет приоритет. Прямой SQL обходит этот механизм ORM.

## Обновление существующей базы

Начальная миграция сохранена. Новая миграция сначала копирует журнал, затем пересоздаёт таблицу прогресса и восстанавливает журнал с новыми ограничениями. Внешние ключи остаются включёнными: [переключение `foreign_keys` внутри транзакции SQLite не действует](https://www.sqlite.org/foreignkeys.html#fk_enable).

Сохраняются все строки, их ID и верхние значения `AUTOINCREMENT`, включая уже удалённые записи. Некорректные существующие данные вызывают полный откат, без удаления или автоматического исправления истории. Тесты проверяют обновление заполненной базы, пустых таблиц с ранее использованными ID, повторное применение миграций и откат при ошибках данных.
