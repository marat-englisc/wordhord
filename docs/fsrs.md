# Ядро обучения карточек: FSRS 6

`src/core/fsrs` использует установленный `ts-fsrs@5.4.2`, который реализует
FSRS 6. Библиотека рассчитывает состояния памяти, интервалы и результаты оценок.
Политика очереди приложения выбирает, какую карточку показать первой.

Единица обучения — **значение слова** (`cardMeaning`), поскольку разные значения
имеют отдельный `userCardMeaning`. Значения одного слова учитываются как соседние
карточки при перемешивании. Таблицы грамматики ядро не читает и не изменяет.

## Как выбирается слово

1. Берутся только карточки колод, добавленных пользователю через `userDeck`.
2. Готовые `Learning`/`Relearning` идут первыми, по точному сроку `due`.
   Шаги заучивания и восстановления разрешены даже после исчерпания дневных квот.
3. Готовые `Review` сортируются по риску забывания и просрочке.
4. Новые значения добавляются после каждых пяти обычных повторений. Если
   повторений нет, новые доступны сразу. Счётчик читается из журнала, поэтому
   это работает и при запросе ботом одной карточки за раз.
5. Новые слова чередуются между активными колодами. Последняя колода хранится
   фактически в журнале ответов: порядок сохраняется после перезапуска и через
   полночь, включая случай, когда предыдущая колода уже исчерпана.
6. Если есть альтернатива, разные значения одного слова разводятся на три
   позиции. Учитываются последние ответы из базы; обработчик может передать
   `recentCardIds` для дополнительно показанных, но ещё не отвеченных карточек.
   Разнесение действует внутри одного уровня приоритета. Если все оставшиеся
   варианты относятся к недавним словам, используется первый подходящий вариант.

Карточки с `due > now` не выдаются раньше срока, даже если срок наступит сегодня.
Для интерфейса возвращаются причины `learning`, `relearning`, `overdue`,
`due_today`, `new`, параметры приоритета и ближайший будущий `nextDueAt`.
Просроченными календарно считаются Review-карточки с due до начала локального дня.
`nextDueAt` показывает ближайший будущий срок, включая сохранённые New-карточки;
он не означает автоматический обход дневной квоты.

## Приоритет повторений

Вероятность воспоминания `R` берётся из
`scheduler.forgetting_curve(elapsedDays, stability)` установленной библиотеки,
с теми же 21 весами, которые используются при вычислении интервалов.
Для приоритета elapsedDays — точное дробное число суток от последнего ответа.
Это позволяет учитывать различия в пределах дня. Сами интервалы и журналы
вычисляет `scheduler.next`; внутреннюю календарную арифметику TS-FSRS ядро не меняет.

Для готовых Review-карточек используется:

```text
a = max(0, (now - due) / 86400000)
q = a / max(1, scheduledDays)

score =
  0.70 * (1 - R)
+ 0.15 * q / (1 + q)
+ 0.10 * a / (7 + a)
+ 0.03 * (difficulty - 1) / 9
+ 0.02 * min(1, lapses / max(1, reps))
```

| Показатель | Для чего нужен |
| --- | --- |
| Риск забывания, 70% | Хрупкое слово может быть важнее очень старого, но хорошо закреплённого |
| Относительная просрочка, 15% | Два дня опоздания при интервале в один день важнее тех же двух дней при интервале в месяц |
| Абсолютная просрочка, 10% | Давно отложенные карточки постепенно получают больше приоритета |
| Сложность, 3% | При прочих равных внимание получает трудное слово |
| Доля ошибок, 2% | Учитываются прошлые провалы, а не только возраст карточки |

Все дополнительные компоненты ограничены. При равном score выбираются ранний
due, затем меньший ID значения. Новые карточки имеют `retrievability: null` и
отдельную очередь: отсутствие памяти не делает новое слово самым срочным
повторением.

Эти коэффициенты — **эвристика приложения**, не обученные параметры FSRS и не
гарантия оптимальности. Формулы памяти и интервалов принадлежат библиотеке.
Веса FSRS можно передать после отдельной оптимизации, но само ядро их не обучает.

## Настройки

| Настройка | По умолчанию |
| --- | --- |
| `request_retention` | 0.9 |
| `maximum_interval` | 36500 дней |
| `enable_short_term` | true |
| `learning_steps` | `["1m", "10m"]` |
| `relearning_steps` | `["10m"]` |
| `enable_fuzz` | true |
| `dailyNewLimit` | 20 значений в день |
| `dailyReviewLimit` | 200 разных Review-значений в день |
| `newCardEvery` | 5 обычных повторений между новыми |
| `backlogSoftLimit` | 50 готовых Review-карточек |
| `backlogHardLimit` | 200 готовых Review-карточек |
| `siblingSpacing` | 3 позиции |
| `queueLimit` | 20 карточек |
| `timeZone` | UTC |

Fuzz распределяет будущие интервалы средствами TS-FSRS. Seed привязан к
пользователю, значению слова и числу повторений; предварительный расчёт и
ответ с одинаковыми входными данными дают одинаковый результат.

При долге до 50 Review-карточек доступен обычный дневной лимит новых.
Между 50 и 200 он линейно уменьшается с округлением вниз.
При 200 и более новые временно отключаются. Если дневной лимит обычных
повторений исчерпан, а готовые повторения ещё есть, новые также не добавляются.
Это ограничивает накопление нового долга, оставляя доступными готовые шаги
заучивания и восстановления.

Лимиты общие для пользователя, даже при выборе одной колоды. Новый слот
расходуется при первом ответе на New-значение, а не при показе или preview.
Повторные Learning/Relearning-шаги не расходуют новый слот. В дневном журнале
считаются разные значения, для которых был ответ из состояния New или Review;
Manual-записи исключаются. Повторная работа с уже учтённым значением в тот же
день не расходует второй слот.

Дневные границы вычисляются в заданной IANA-зоне, включая дни длиной 23/25 часов
при переходах DST. Часовой пояс процесса Node.js не влияет на квоты. Для
пользователя используйте его постоянную зону в обработчиках; не переключайте
её произвольно между ответами.

## API

```ts
import { Rating } from "ts-fsrs";
import { createStudyService, StudyError } from "./core/fsrs";

const study = createStudyService({
  policy: {
    timeZone: "Europe/Moscow",
    dailyNewLimit: 20,
    dailyReviewLimit: 200,
  },
  fsrs: {
    request_retention: 0.9,
    enable_fuzz: true,
  },
});

// userId — внутренний user.id, а не Telegram ID.
const queue = await study.getStudyQueue(userId, { deckId, limit: 20 });
const item = queue.items[0];

if (item) {
  const preview = await study.previewCardReview(userId, {
    cardMeaningId: item.meaning.id,
    version: item.version,
  });

  // Покажите item.card.title и нужный контекст, а ответ — после попытки вспомнить.
  // preview.outcomes[Rating.Good].progress.due — возможный срок следующего показа.
  try {
    const result = await study.reviewCard(userId, {
      cardMeaningId: item.meaning.id,
      version: item.version,
      rating: Rating.Good,
    });
    // result.progress и result.review уже сохранены; запросите следующую карточку.
  } catch (error) {
    if (error instanceof StudyError && error.code === "STALE_CARD") {
      // Ответ уже обработан или карточка изменилась: обновите показ.
    } else {
      throw error;
    }
  }
}
```

Для запроса по одной карточке есть
`study.getNextStudyCard(userId, { deckId? })`, возвращающий запись или `null`.
Методы можно деструктурировать. Также экспортируются одноимённые функции
`getStudyQueue`, `getNextStudyCard`, `previewCardReview`, `reviewCard` с настройками
по умолчанию. Для пользовательских настроек создавайте сервис явно.

`getStudyQueue` возвращает `items`, `generatedAt`, `day`, `nextDueAt`, `counts`.
Каждый элемент содержит карточку, значение, колоду, собственный прогресс,
`version`, `reason`, `priority`. В counts:

- `dueLearning`, `dueReview`, `overdueReview` — готовые карточки выбранных колод;
- `globalDueReview` — долг всех активных колод, используемый для ограничения новых;
- `introducedToday`, `reviewedToday`, `answersToday` — дневная активность;
- `newRemaining`, `reviewRemaining` — оставшиеся дневные слоты до выдачи очереди.

Узкий запрос колоды не обходит долг остальных колод. Запрос к отсутствующему
пользователю или чужой колоде завершается ошибкой. Если активных колод нет,
возвращается пустая очередь.

Оценки: `Again=1` — не вспомнил, `Hard=2` — вспомнил с трудом,
`Good=3` — вспомнил, `Easy=4` — вспомнил легко.
`Manual=0`, дробные и нечисловые оценки не являются ответами ученика.
Preview не расходует лимиты и не пишет в базу; при отправке ответа лимиты
проверяются заново. Между показом и ответом расчёт будущего интервала может
измениться из-за нового времени ответа.

## Согласованность и ошибки

Получение очереди выполняется согласованным чтением без создания прогресса.
Прогресс отсутствующего значения создаётся при первом успешном ответе, с полями,
рассчитанными `createEmptyCard` и `next`.

При ответе выполняется одна SQLite-транзакция `BEGIN IMMEDIATE`:

1. Проверяется принадлежность колоды и актуальный прогресс.
2. Проверяются версия, точный срок и текущие глобальные квоты.
3. TS-FSRS вычисляет следующий прогресс и журнал.
4. Сохраняются прогресс, полный журнал и `userDeck.lastReviewedAt`.

Ошибка любого шага откатывает все записи. Версия — отпечаток всей предыдущей
записи прогресса, включая владельца, ID, даты и счётчики. Двойное нажатие даёт
один успешный ответ и `STALE_CARD` для повторного; счётчик не увеличивается дважды.
Версия служит для контроля актуальности, а авторизованный `userId` обработчик
определяет по отправителю Telegram-сообщения.

В журнал сохраняются все поля, включая `lastElapsedDays` и `learningSteps`.
`log.due` сохраняется буквально из TS-FSRS: у изученной карточки он может
соответствовать предыдущему `last_review`, а не старому сроку показа.
Новое due всегда находится в возвращённом прогрессе.

| Код StudyError | Причина |
| --- | --- |
| `USER_NOT_FOUND` | Пользователь отсутствует |
| `CARD_NOT_AVAILABLE` | Карточка или колода не принадлежит активной коллекции |
| `STALE_CARD` | После показа прогресс уже изменился |
| `CARD_NOT_DUE` | Следующий срок ещё не наступил |
| `DAILY_LIMIT` | Дневная квота или допустимый новый объём исчерпаны |
| `INVALID_PROGRESS` | Сохранённое состояние памяти неполное или неверное |

Неверные аргументы и настройки вызывают `RangeError`/`TypeError`.
Ядро не восстанавливает отсутствующий lastReview или память изученной карточки
догадками. `now`/`clock` предназначены для серверного времени и тестов: клиент не
должен задавать произвольное время ответа.

## Хранение и проверка

Словарь хранится в `content.db`, прогресс и журнал — в `users.db`.
Общее соединение с ATTACH сохраняет JOIN и транзакционный ответ FSRS;
устройство хранения описано в [databases.md](databases.md).
Специализированный `studyRepository` отделяет операции SQL от чистого
`engine`, политики и ранжирования. Фабрики позволяют подставить временные SQLite-файлы
и управляемые часы для тестов.

Готовые повторения ранжируются целиком: стоимость чтения и оценки линейна от
размера долга, сортировки — O(N log N). Это сохраняет корректное сравнение риска
вместо преждевременного SQL LIMIT по due. Версии рассчитываются только для
выбранных карточек. Новые кандидаты ограничиваются по числу разных слов в каждой
колоде; десятки значений одного слова не вытесняют другие слова из пула.
Используется синхронный драйвер Node SQLite, поэтому чтение и расчёт выполняются
в потоке приложения.

`npm test` проверяет FSRS-ответ через две базы, совпадение preview и результата,
защиту от повторного ответа, откат прогресса/журнала/lastReviewedAt, независимость
грамматики. Базы приложения и Telegram при тестировании
не используются.
