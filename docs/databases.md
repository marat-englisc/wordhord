# Контент и пользовательские данные в разных SQLite-файлах

Приложение использует два физических файла:

| Файл | Таблицы |
| --- | --- |
| `content.db` | `deck`, `attribute`, `card`, `card_meaning`, `card_example`, `card_meaning_attribute`, `rule`, `rule_image`, `rule_section`, `rule_section_example`, `rule_section_primary_info` |
| `users.db` | `user`, `user_deck`, `user_card_meaning`, `user_card_meaning_review`, `user_rule`, `user_rule_comment` |

В контенте находятся словарь, колоды, примеры, атрибуты и грамматика.
Пользовательская база содержит аккаунты, выбранные колоды и правила, личные
заметки, память FSRS и историю ответов. Статистика рассчитывается из этой истории.
FSRS применяется только к карточкам, единицей обучения остаётся `cardMeaning`.

## Настройка и создание

В `.env`:

```dotenv
CONTENT_DATABASE_URL=./content.db
USERS_DATABASE_URL=./users.db
```

Это также значения по умолчанию. Используйте обычные пути, без `file:`.
Относительные пути отсчитываются от рабочей директории команды; запускайте её
из корня проекта. Родительские каталоги должны существовать. Пути должны вести
к разным физическим файлам. Для соединения приложения `:memory:` не используется,
поскольку гарантии атомарности между файлами требуют файловой основной базы.

Для новой установки:

```sh
npm run db:migrate
npm run build
npm start
```

## Подключение и репозитории

`openApplicationDatabase({ contentPath, usersPath })` из `src/db/connection.ts`
открывает `users.db` как `main` и подключает `content.db` через параметризованный
`ATTACH DATABASE ? AS content`. Один `DatabaseSync` и один Drizzle `db` обслуживают
обе базы. Закрытие `db.$client.close()` закрывает всё соединение.

Репозитории используют `getDatabase()` из `src/config/db.ts`: общее соединение
создаётся при первом обращении и освобождается через `closeDatabase()`.
Импорт модулей не создаёт и не проверяет SQLite-файлы. Фабрике
`createStudyRepository(database)` можно передать отдельное соединение;
`createStudyService({ repository })` работает без стандартных баз.
SQLite разрешает
имена таблиц без префикса, если эти имена не повторяются между файлами. При открытии
проверяется, что пользовательские таблицы отсутствуют в контенте и наоборот.
Поэтому `getDecksForUser`, `getRulesForUser`, получение карточки с материалами
и запросы очереди FSRS продолжают работать через JOIN. В сыром SQL используйте
явные префиксы `main.user_card_meaning`, `content.card_meaning`.

Ответ FSRS сохраняет прогресс, журнал и `lastReviewedAt` одной транзакцией в
`users.db`. Общий контент при ответе не меняется. Транзакция, которая удаляет
контент и его пользовательские ссылки, охватывает оба файла.

Обе базы используют `journal_mode=DELETE` и `synchronous=FULL`, с ожиданием
блокировки до пяти секунд. Не переключайте эту пару на WAL: SQLite гарантирует
атомарность многофайлового COMMIT при файловой `main` и rollback-журналах;
при WAL авария во время COMMIT может оставить файлы в разных состояниях.
См. [официальную документацию ATTACH](https://sqlite.org/lang_attach.html).

## Связи между файлами

SQLite [не поддерживает внешние ключи между схемами](https://www.sqlite.org/foreignkeys.html).
Обычные внешние ключи сохраняются **внутри** каждого файла:

- карточки, значения, примеры и материалы грамматики связаны в `content.db`;
- пользователь связан с прогрессом, колодами, правилами и заметками в `users.db`;
- составной FK журнала проверяет владельца, значение и состояние изучения.

Четыре связи на контент — `user_deck.deck_id`,
`user_card_meaning.card_meaning_id`, `user_rule.rule_id`,
`user_rule_comment.rule_id` — защищаются TEMP-триггерами соединения:

1. INSERT/UPDATE отклоняется, если контента с таким ID нет.
2. Удаление значения удаляет весь его пользовательский прогресс и журнал;
   удаление пустой колоды — подписки; удаление правила — ссылки и личные заметки.
3. Смена ID контента, на который есть пользовательские ссылки, запрещена.

Внутренний `ON DELETE RESTRICT` колоды сохраняется: сначала нужно удалить
её карточки. Удаление аккаунта удаляет его персональные строки и сохраняет контент.

TEMP-триггеры пересоздаются при каждом подключении. По
[правилам SQLite](https://sqlite.org/lang_createtrigger.html#temp_triggers_on_non_temp_tables)
они действуют только в соединении, которое их создало. Поэтому редактирование
через отдельный SQLite-редактор не выполняет межфайловые каскады и проверки.
Изменяйте данные через репозитории или `openApplicationDatabase`. При запуске
проверяются внутренние FK и наличие всех объектов контента, на которые ссылается
пользовательская база; несовместимая пара файлов вызывает ошибку.

ID контента должны оставаться стабильными. Нельзя заменить `content.db` сборкой,
в которой те же ID присвоены другим словам или правилам: проверка существования
ID не определяет такое изменение смысла. Для резервного копирования остановите
записи приложения и сохраните согласованную пару файлов. `users.db` можно
восстановить отдельно при наличии соответствующего контента с теми же ID.

## Миграции

| База | Конфигурация | Каталог миграций |
| --- | --- | --- |
| Контент | `drizzle.config.ts` | `drizzle/content` |
| Пользователи | `drizzle.users.config.ts` | `drizzle/users` |

`npm run db:generate` создаёт миграции для обеих схем. Для отдельной схемы есть
`npm run db:generate:content` и `npm run db:generate:users`.
`npm run db:migrate` предварительно проверяет назначение обоих файлов и применяет
каждую историю отдельно. У каждого файла собственная `__drizzle_migrations`.
Изменение данных внутри одной миграции транзакционно; применение двух независимых
историй не является одной общей транзакцией. После ошибки устраните причину
и повторите команду.

Миграция обязательных полей журнала сохраняет существующие ненулевые значения.
Для старого `NULL` в `last_elapsed_days` используется `elapsed_days` предыдущей
записи того же прогресса по `review, id`; при отсутствии предыдущей записи —
`elapsed_days` текущей. Неизвестные `learning_steps` получают `0`.
Это backfill неполной истории; точные отсутствовавшие шаги восстановить нельзя.

Миграция `progress_integrity` добавляет границы чисел и дат и индекс
`(user_id, state, review)`. Если старые значения нарушают ограничения, миграция
завершается ошибкой с откатом; исправьте данные и повторите команду.
При пересоздании таблиц сначала копируются прогресс и журнал, затем удаляются
старые таблицы: `PRAGMA foreign_keys=OFF` внутри транзакции мигратора не действует.

## Проверка

`npm test` собирает TypeScript и проверяет физическое разделение, существующие
репозитории и JOIN, FSRS и защиту от повторного ответа, каскады, откат обеих баз,
повторное открытие и команду миграций.
Тесты используют временные SQLite-файлы и не подключаются к Telegram или базам
приложения.
